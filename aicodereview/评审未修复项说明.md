# AI 评审未修复项说明

针对 `aicodereview/` 下两份评审报告（2018 报告 6 项、2021 报告 18 项，另有 4 条架构建议），
在 **2021 分支**完成了可修复项的修复（见文末"已修复清单"）。
本文档说明 **未修复项及理由**，并附实证。所有实证基于 `rustc 1.98.0`。

---

## 一、未修复项（6 项）

### N1. "Edition 降级/回退" —— 设计使然，不修

**来源：** 2018 报告 Major「Edition 回退至 2018 可能导致依赖不兼容」；2021 报告 Critical「Rust edition 从 2024 降级到 2021 可能导致兼容性问题」；架构建议 2018-A1、2021-A1。

**不修理由：** 本仓库是多 Edition 教学仓库，`2015 / 2018 / 2021 / 2024` 四个分支各自持有对应
`edition` 值是刻意设计，而非疏忽回退。评审以"单一主分支"视角判断为降级，与仓库机制不符。

**实证：** 四个分支 `cargo build --bins` 均 0 error 0 warning（targets 148/151/152/153），
`cargo test` 均 0 failed。当前 2021 分支构建、测试同样全绿。

### N2. Blocker「expr_2021 宏片段说明符不是标准 Rust 语法」—— 误报，不修

**来源：** 2021 报告第 1 轮 Blocker + 第 2 轮 Blocker（同一问题两次上报）；
架构建议 2021-A1 亦引用它断言"项目无法通过 cargo build"。

**不修理由：** `expr_2021` 是合法片段说明符（RFC 3086），当前工具链完全接受。

**实证：**

```
cargo run -q --bin 21_macros_macros4
→ Check out my macro!
  Look at this other macro: 7777
  exit code 0
```

### N3. Critical「`#[unsafe(no_mangle)]` 在 Rust 2021 中不支持」—— 误报，不修

**来源：** 2021 报告第 2 轮 Critical（`src/bin/keywords_extern.rs` L15）；架构建议 2021-A1。

**不修理由：** `unsafe` 属性自 Rust 1.82 起稳定，且适用于**所有** Edition；
Rust 2024 只是把不带 `unsafe` 的旧写法在 2024 Edition 下变为硬错误。评审把
"2024 的收紧规则"错误外推到了 2021。

**实证：**

```
cargo run -q --bin keywords_extern
→ Using extern keyword example
  rust_function(5, 7) = 12
  exit code 0
```

### N4. Minor「移除冗余的 `use std::iter::FromIterator;`」—— 跨分支必需，不修

**来源：** 2021 报告第 2 轮（`hashmaps2.rs` 测试模块）。

**不修理由：** `FromIterator` **不在** Rust 2015/2018 的 prelude 中，缺导入直接
`E0599`（本仓库 2015 分支此前已实测）。该 import 在 2021 下虽冗余但不产生任何警告，
保留它可使文件在四个分支内容一致，避免 merge 链反复冲突。

### N5. Minor「恢复使用 Rust 2021 新式格式化语法（panic!）」—— 2015 分支必需旧式，不修

**来源：** 2021 报告第 2 轮（测试代码中的 `panic!("... {:?}", x)`）。

**不修理由：** 在 Edition 2015 下，`panic!` 单参数不做格式化（隐式捕获触发
`non_fmt_panics` 警告，本仓库 2015 分支已实测）。旧式 `panic!("... {:?}", x)`
在**全部四个 Edition** 均有效且零警告。为跨分支一致性保留旧式写法。

### N6. 架构建议 2021-A2「移除约 50 个 [[bin]] 条目可能影响外部引用」—— 无需修改

**来源：** 2021 报告架构建议第 2 条。

**不修理由：** 文件迁至 `src/bin/` 后由 Cargo `autobins` 自动发现，**bin 名称全部保留**
（文件名即 bin 名），`cargo run --bin <原名>` 不受影响。`Cargo.toml` 注释已补充说明这一点。

**实证：** `cargo run --bin <不存在名>` 触发的可用目标列表包含全部原名称，如
`keywords_break`、`keywords_extern`、`edition_2015`、`20_threads_threads3` 等。

| 2018-A1 构建一致性风险（edition 回退 vs 练习代码） | 同 N1：四分支构建/测试全绿，实证无风险 |

## 三、评审建议被适配（2 处，AI 建议本身不成立）

1. **`struct _Parser<'_>`**（2018 报告「匿名生命周期示例」、2021 报告「修正匿名生命周期演示代码」）：
   AI 给出的目标代码 `struct _Parser<'_> { input: &'_ str }` **无法编译**
   （`'_` 不能作结构体参数名，E0637；字段缺具名生命周期，E0106）。
   已适配为：函数参数/返回值用 `&'_ str`，结构体保持具名 `'a`，另用
   `impl _Parser<'_ { ... }`（`'_` 的标准合法场景）演示。
2. **enums2「移除文件级 allow」**：AI 断言"字段实际都被使用"不成立——
   字段仅经 `#[derive(Debug)]` 输出（derive 不计入 dead_code 分析），移除后实测 5 条
   `field is never read` 告警。已按其备选方案改为 **条目级** `#[allow(dead_code)]`
   并注明原因（练习字段，留待读者显式读取），traits3/traits5 同理。

## 五、分支范围说明

以上修复仅落在 **2021 分支**（按"当前分支解决"要求）。本仓库 merge 链方向为
`2015 → 2018 → 2021 → 2024`（单向向上），因此：

- 修复会随下一次 merge 流入 **2024 分支**；
- **2015 / 2018 分支**不会自动获得这些修复（如 2018 分支的 `edition_2018.rs`
  仍保留 `await!` 旧文案、README 仍为空标题）。如需同步，可在对应分支单独
  cherry-pick 或调整 merge 方向。
