**线程句柄未被 join 可能导致资源清理不及时**

> 🟢 **Minor** | 🧹 **Code Smells**

### 📋 问题详情

当前代码通过 `thread::spawn` 创建了两个子线程，但没有保存它们的 `JoinHandle` 并在函数结束前 join。虽然在这个特定场景下，由于 `mpsc::channel` 的语义（所有 Sender 关闭后 Receiver 迭代结束），程序行为是正确的，但在生产代码中，不 join 线程可能导致：

1. **资源泄漏风险**：线程占用的栈空间和系统资源可能不会立即释放
2. **错误处理缺失**：无法捕获线程 panic 或其他异常
3. **执行顺序不确定**：调用者无法确定线程何时完成

保存 `thread::spawn` 返回的 `JoinHandle`，并在函数结束前调用 `.join().unwrap()` 等待线程完成。这样可以确保：
- 线程资源被正确清理
- 任何线程 panic 都会被传播到主线程
- 函数返回时所有工作已完成

**README 中关于 Rust 2021 闭包自动解引用的描述存在技术错误。**

> 🟡 **Major** | 🧹 **Code Smells**

### 📋 问题详情

README.md 中声称 Rust 2021 edition 引入了闭包参数的"自动解引用"功能，使得 `divide(n, 27)` 可以直接接受 `&i32` 类型的 `n` 并自动转换为 `i32`。这是不准确的。

实际上：
1. `into_iter()` 对数组 `[i32; N]` 产生的是值迭代器（`i32`），而不是引用迭代器（`&i32`）。因此在 2018 和 2021 edition 下，`n` 的类型都是 `i32`，不需要解引用。
2. Rust 2021 的闭包捕获改进主要涉及**部分移动**（partial moves）和**精确捕获**（precise capturing），即闭包只捕获实际使用的字段而非整个结构体，这与参数类型的自动解引用无关。
3. 如果使用的是 `iter()` 而非 `into_iter()`，则 `n` 的类型是 `&i32`，此时无论哪个 edition 都需要显式解引用 `*n` 或使用 `n` 的自动解引用特性（通过 `Deref` trait），但这与 edition 无关。

当前描述会误导读者对 Rust 所有权系统和 edition 差异的理解。

### 💡 解决方案

修正 README 中的技术描述：
1. 明确 `into_iter()` 对数组产生值迭代器，`n` 类型为 `i32`，无需解引用。
2. 如果要展示 2021 edition 的闭包改进，应使用涉及结构体部分移动的例子，例如：
   ```rust
   struct Config { count: i32, value: String }
   let config = Config { count: 1, value: "hello".to_string() };
   let closure = || println!("{}", config.count); // 2021: 只捕获 count，value 仍可用
   println!("{}", config.value); // 2018: 这会报错，因为整个 config 被移动
   ```
3. 删除关于"自动解引用"的错误说法。
